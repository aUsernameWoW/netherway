# Netherway 中文文档

[返回项目主页](../../README.md) | [English](../en/README.md)

## 前提

服务端只需要一个能被外网访问的 Minecraft 入口——樱花 frp、花生壳、云主机
上的一条 NAT 规则、nginx stream，任何能把 TCP 转到 MC 端口的第三方转发都
可以。Netherway 不要求转发方支持任何特定协议，也不需要服主再架设任何
其它服务。

打洞成功后游戏流量不经过第三方；打不通时玩家仍在原有转发线路上正常游玩。

## 怎么工作

```text
游戏服务器                       端口转发                    玩家
  │                               │                        │
  ├─ 内嵌信令点 ◀── 经 MC 端口转入 ─┼──── 信令（打洞前）────┤
  │                               │                        │
  └──────── P2P 直连，不经过第三方 ─────────────────────────┘
```

mod 自带一个 agent（打洞与隧道程序），由 mod 自动启停，玩家无需安装或运行
任何额外程序。服务端 mod 在 MC 服务端进程内嵌一个只监听本机回环的信令点，
玩家的信令连接经既有的端口转发到达 MC 端口后，由 mod 识别并转入信令点。
两端交换完地址信息就开始打洞，打通后的游戏流量在两端之间直接传输。
整个过程不依赖任何公共第三方服务器。

## 安装

从 [GitHub Releases](https://github.com/aUsernameWoW/netherway/releases) 下载与你的 Minecraft 版本和平台匹配的 Netherway：

- Forge / Fabric 版：客户端和服务端分别放入对应实例的 `mods/` 文件夹。
- Bukkit 版（Spigot/Paper 1.13+）：放入服务端的 `plugins/` 文件夹。

首次启动会自动生成 `<MC服务端根目录>/config/netherway.cfg`。默认配置开箱
即用，通常不需要修改；如有需要按下文修改，重启 MC 服务端后生效。

## 服务端配置

新生成的默认配置关键部分如下：

```text
server {
    B:enabled=true
    B:runAgent=true
    B:rendezvous=true
    S:backend=gonc-p2p
    S:params <
        sessionKey=auto
        room=minecraft
     >
}
```

- `rendezvous=true`：信令点内嵌在 MC 服务端进程里，玩家的信令经 MC 端口
  转入。保持默认即可。
- `sessionKey=auto`：会话密钥随服务端每次重启自动轮换，旧凭证自动失效；
  玩家侧会自动取回新凭证，无需任何操作。保持默认即可。
- `room=minecraft`：房间名，只用于显示与区分；如需修改，使用不包含空格的
  英文名称。

同一台机器可以运行多个 Netherway 服务端。只要每个服务器拥有不同且稳定的
公网 `host:port` 入口，它们可以继续使用相同的默认房间名；客户端会按服务器
入口分别保存凭证和预热状态。

注意 cfg 的语法细节：键有类型前缀（`B:` 布尔、`S:` 字符串、`I:` 整数），
列表以 `S:params <` 开始、单独一行的 `>` 结束。配置只在启动时读取，改动需
重启。语法错误不会炸服：mod 会记录错误并在本次启动关闭服务端直连，修正后
重启即可。

## 可选功能

### 外部信令 broker（`server.params` 里的 `brokers`）

默认情况下信令点内嵌在服务端进程里、只走 MC 端口，这是推荐形态。若你
更愿意使用公共或自建的 MQTT broker，在 `server.params` 里加一行
`brokers=tcp://broker.example.com:1883`（多个以逗号分隔）并把
`rendezvous` 设为 `false`。这样凭证里会带上 broker 地址，玩家的信令直接
连向它，不再经过 MC 端口。

### 邀请码（没有任何公网入口的服务器）

服务器连一个能被外网访问的 Minecraft 入口都没有（不做端口转发、也不租
中转）时，凭证没法经登录或预认证送到玩家手上。这种情况下改用公共（或自建）
信令 broker，再把凭证折成一段**邀请码**交给玩家：

1. 在 `server.params` 里写上 `brokers=tcp://broker.example.com:1883`
   （逗号分隔多个），并把 `rendezvous` 设为 `false`。
2. 启动服务端，日志里会出现一行 `邀请码: nw1-…`。
3. 玩家在多人游戏界面「添加服务器」，把这段邀请码**原样粘贴进服务器地址栏**，
   名字随意。mod 会立刻开始为它打洞；打通后点击该条目即直连，列表上显示的
   延迟就是直连延迟。没打通时该条目显示无法连接。

邀请码就是会话密钥：拿到它的人就能建立到 MC 端口的隧道，准入仍由 MC 服务端的
白名单/正版验证决定。`sessionKey=auto` 下密钥每次重启轮换，邀请码也随之变化，
要发一个长期有效的邀请码就在 `server.params` 里写一个固定的 `sessionKey`。
邀请码必须放得进服务器地址栏（128 字符）：默认参数约 50 字符，两个 broker
也放得下；列表太长时启动日志会说明。删掉列表里的邀请码条目，对应隧道随之关闭；
邀请码不会写进客户端的凭证缓存，条目本身就是来源。

### PROXY protocol（`server.proxyProtocol`）

设为 `v2`（或 `v1`）后，经直连隧道进入的连接会携带玩家真实来源地址，
使服务端日志和封禁看到玩家真实 IP 而不是 `127.0.0.1`。它只对直连隧道的
连接生效，对经端口转发进来的连接无影响。

### 打洞超时（`server.punchTimeoutSeconds`）

服务端可以向客户端建议一个打洞超时（秒），0 表示由客户端自己配置
（`client.punchTimeoutSeconds`，默认 15）。网络环境较差、经常要第二轮
才能打通时可适当调大。

### 预认证（`server.preauth`）

默认开启：客户端启动时就能向 MC 端口请求凭证，从而在进服前完成打洞。
关闭后玩家只能在进服后拿到凭证，直连要等登录后的一次重连才生效。

## 客户端

客户端安装对应平台的 Netherway 后无需配置。

客户端启动时会向服务器列表里的所有候选并行预取凭证，再为每个成功应答的服务串行打洞。串行打洞可以避免同一 NAT 上的多次尝试互相干扰；已经建立的多条隧道可以同时存活。

默认情况下，预热成功后玩家点击原服务器条目就会直接使用本地 P2P 隧道；`servers.dat` 中的真实地址不会被修改，所以下次启动、预取失败或移除 mod 后仍可使用原线路。若玩家在预热完成前已经进入服务器，预热成功后会立即切换。某个服务打不通时，它会独立退避并重试，不影响其他服务。

将 `client.replaceServerEntries` 设为 `false` 可改为额外维护 `[P2P直连] <房间> (<入口>)` 条目，让原入口和直连入口同时显示。

服务器列表里以 `nw1-` 开头的条目会被当作邀请码（见上文），无需其它设置。

## 已知限制

- 打洞成功率取决于两端 NAT 类型。一端是对称 NAT 时成功率明显下降，两端都是
  对称 NAT 时基本失败。失败时玩家仍在原有转发线路上，不影响游玩。
- 刻意不做中转兜底：打不通就留在原线路，不会额外经第三方中转一遍。
- 服务端与客户端都必须装 mod；没装 mod 的客户端照常进服，只是走原线路。
- Windows 首次运行可能弹出防火墙提示。
- 吞吐受连接双方上传带宽限制，家宽通常限制较多，因此无论是否直连都不适合大流量传输场景。

## 从源码构建

```bash
go build ./... && go test ./...          # agent（Go 1.26）
./mod/build-natives.sh                    # 打进 jar 的跨平台 agent 二进制
cd mod/platform/forge-1.7.10 && ./gradlew build
```

产物位于 `build/libs/`。Gradle 需要 Java 21+，编译产物为 Java 8 字节码。
构建不需要任何密钥或部署参数：凭证全部由服务端在运行期生成并下发。
